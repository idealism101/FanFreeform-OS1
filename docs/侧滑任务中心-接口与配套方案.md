# 侧滑任务中心模块 · 接口定义与配套方案

> 目标读者：需要**仅凭本文档**重新实现（或移植、替换）此模块的开发者。
> 本文所有签名、常量、调用链均取自仓库真实代码（HEAD `a02b7e7`），不再重述推测。
> 无法从代码确证的内容统一收入第 11 章「待确认项」，不在正文里含糊带过。

---

## 0. 一句话定义

在**侧边手势**拉出的浮层里，展示系统最近任务的应用卡片列表，并让用户对任一应用执行
**启动 / 关闭 / 小窗 / 分屏 / 锁定 / 查看应用信息 / 启动其桌面快捷方式 / 全局搜索**
八类动作。所有动作最终都落到系统原生接口，模块**不自建窗口管理、不自建状态存储**。

## 1. 模块边界

### 1.1 职责（模块负责）

| 负责 | 说明 |
|---|---|
| 手势 → 列表的唤起 | 判断侧边布局档位是「任务」档，读取任务数据并让浮层上屏 |
| 列表的呈现与交互 | 绘制面板/卡片、命中判定、菜单展开、手势跟手、四类出场动画 |
| 动作分派 | 把用户点选翻译成对系统原生接口的调用 |
| 列表窗口的生命周期 | 何时上屏、何时让位、何时销毁（含五条主动关闭通路） |

### 1.2 非职责（模块明确不做）

| 不负责 | 归属 |
|---|---|
| 任务栈的真实管理 | system_server（`ActivityTaskManagerService`） |
| 小窗窗口的创建/缩放/停靠 | MIUI `MiuiFreeformModeController` |
| 分屏 stage 的布局与过渡 | MIUI `SoScSplitScreenController` / `SoScStageCoordinator` |
| 锁定状态的权威存储与 adj 调整 | system_server `ProcessManagerService` / `ProcessPolicy` |
| 任务快照的生成 | system_server（`getTaskSnapshot` / `takeTaskSnapshot`） |
| 关闭时机由系统代劳 | **刻意放弃**，改由本模块订阅系统信号后主动撤窗（见 6.3） |

## 2. 进程与线程模型（重构前必读）

### 2.1 三个进程

| 进程 | 关键持有物 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **SystemUI**（`com.android.systemui`） | `FanRuntime`、`TaskSwitcherOverlayController`、`RecentTaskRepository`（主调用点）、`LockedAppStore`、`HyperOsFreeformBridge`、`SoScSplitScreenController` 实例 | 读任务栈（持 `GET_TASKS`）、反射 AMS、调小窗/分屏原生对象、添加 `ty=2038` 浮窗 | 无法成为系统认定的「当前界面」 |
| **模块进程**（`com.oxohang.fanfreeform`） | 设置界面、`ConfigProvider` | 承载普通 Activity（`ty=1`）、读写配置 | **CAP 位为 0，查 `ActivityManager` 恒返回空列表** |
| **桌面**（`com.miui.home`） | `RecentsContainer` | 系统原生最近任务 UI | — |

### 2.2 由此导出的两条硬约束

**约束 A：任务数据只能在 SystemUI 进程读。**
`RecentTaskRepository` 的 `activityTaskManagerService()` 走反射 + `ActivityTaskManager.getService()`，
依赖 SystemUI 进程已持有的权限。模块进程调用同一份代码会得到空结果。

**约束 B：`RecentTaskRepository` 不得引用任何 Xposed 类。**
该类历史上被两个进程共用。模块进程**没有 Xposed 运行时**（类加载器里不存在
`de.robv.android.xposed.*`），一旦引用 `XposedHelpers` 就 `NoClassDefFoundError` 并连带宿主崩溃。
所以它用标准 `java.lang.reflect` 手工反射（见该类 `invoke()`，第 343 行）。
**重构时必须保留这个约束**，否则模块进程一碰就崩。

### 2.3 线程

| 线程 | 用途 | 关键点 |
|---|---|---|
| 主线程（SystemUI 的 Looper） | 窗口 add/remove、视图动画、`WindowManager` 操作 | 所有 `WindowManager` 调用必须在此线程 |
| `configHandler` | 后台读任务列表（`loadRunningTasks` 走 Binder，会阻塞） | 读完后 `mainHandler.post` 回主线程上屏 |
| 视图自身 Handler | `TaskSwitcherOverlayController.runOnViewThread` 的投递目标 | 跨线程时通过 `Surface.getHandler()` 判断并 post |

## 4. 数据结构

### 4.1 `RecentTaskPreview`（`xposed/RecentTaskPreview.java`）

一条任务的最小视图模型，**不可变**。

| 字段 | 类型 | 含义 | 可空 |
|---|---|---|---|
| `taskId` | `int` | 系统任务 id，所有后续动作的主键 | 否 |
| `packageName` | `String` | 包名，小窗/锁定/应用信息用 | 否 |
| `label` | `CharSequence` | 应用名，列表展示用 | 是 |
| `snapshot` | `Bitmap` | 任务快照（**可能为 hardware bitmap**） | 是 |
| `icon` | `Drawable` | 应用图标 | 是 |

**快照生命周期**：`snapshot` 由 `RecentTaskRepository.loadSnapshot()` 通过
`Bitmap.wrapHardwareBuffer()` 包装 `HardwareBuffer` 得到。**必须**在某处调用
`RecentTaskRepository.release(List<RecentTaskPreview>)` 回收（内部 `snapshot.recycle()`），
否则 hardware bitmap 会耗尽显存。调用点：`FanRuntime.showLoadedSideTasks` 的空列表分支
与 `TaskSwitcherOverlayController.removeNow → releaseResources`。

### 4.2 `RecentTaskRepository.ShortcutEntry`（静态内部类）

应用自己发布的桌面快捷方式。

| 字段 | 类型 | 含义 |
|---|---|---|
| `packageName` | `String` | 宿主包 |
| `id` | `String` | 快捷方式 id |
| `label` | `CharSequence` | 显示名 |
| `user` | `UserHandle` | 所属用户 |

### 4.3 `TaskSwitcherOverlayController.Surface`

呈现层的统一抽象。两个实现：`TaskCenterListView`（第三档）、`TaskSwitcherOverlayView`（视差卡片）。

| 方法 | 签名 | 职责 |
|---|---|---|
| 入场 | `void playEntry()` | 播放入场动画 |
| 外部移动 | `void onExternalMove(float x, float y)` | 手指在覆盖层上的移动 |
| 外部抬起 | `void onExternalUp(float x, float y, boolean cancelled)` | 手指抬起 |
| 外部取消 | `void onExternalCancel()` | 手势流被系统取消 |
| 出场 | `void playDismissal()` | 播默认出场 |
| 释放 | `void releaseResources()` | 撤窗后释放（位图、监听器） |
| 取 Handler | `Handler getHandler()` | 供控制器跨线程投递 |

### 4.4 `TaskCenterListView.Listener` / `TaskSwitcherOverlayController.Listener`

两层 Listener 签名**一致**，控制器做一层转发（并在转发处决定是否播放让位动画）。

```java
// TaskCenterListView.Listener（视图 → 控制器）
void onLaunch(RecentTaskPreview task);                                     // 点行本体
void onCloseTask(RecentTaskPreview task);                                  // 点行尾关闭区
void onCloseAll();                                                         // 点底部「全部关闭」
void onListAction(int action, RecentTaskPreview task,
                  RecentTaskRepository.ShortcutEntry shortcut);             // 点菜单项
void onToggleLock(RecentTaskPreview task, boolean shouldLock);             // 点行内锁形
void onClosed();                                                           // 出场动画结束
```

`TaskSwitcherOverlayController.Listener` 在此基础上**多一个方法**（因为控制器要感知窗口生命周期）：

```java
void onClosed();   // 控制器已撤窗（removeNow 之后）
```

### 4.5 动作码（`TaskCenterListView` 静态常量）

| 常量 | 值 | 菜单文案 | 是否关列表 |
|---|---|---|---|
| `ACTION_LOCK` | 0 | 锁定此应用程序 | **是**（`EXIT_YIELD`） |
| `ACTION_SPLIT` | 1 | 在分屏视图中打开 | **是**（`EXIT_YIELD`） |
| `ACTION_FREEFORM` | 2 | 在弹出视图中打开 | **是**（`EXIT_YIELD`） |
| `ACTION_DETAILS` | 3 | 应用程序信息 | **是**（`EXIT_YIELD`） |
| `ACTION_SHORTCUT` | 4 | （快捷方式名，动态） | **是**（`EXIT_YIELD`） |
| `ACTION_SEARCH` | 5 | （底部搜索按钮，不进菜单） | 否（`handleTap` 直接回调，不 `playExit`） |

> ⚠️ `ACTION_LOCK`（菜单项）与 `onToggleLock`（行内锁形）**最终动作相同**，但前者关列表、后者不关。
> 这是刻意设计：锁形是"开关"，用户会连着锁多个；菜单项是"一次性命令"。

### 4.6 出场因果码（`TaskCenterListView` 静态常量）

| 常量 | 值 | 语义 | 目标形态 | 时长 |
|---|---|---|---|---|
| `EXIT_RECEDE` | 0 | 点外部 / 返回键 | 回落，与入场反演 | 200ms |
| `EXIT_YIELD` | 1 | 点应用 / 菜单项（给目标让位） | 位移 −12dp + 缩至 0.92 + 淡出 | 220ms |
| `EXIT_FLING` | 2 | 跟手上划甩出 | 移出屏外，速度决定时长 | 180–340ms |
| `EXIT_QUIET` | 3 | 系统事件（开小窗等） | 只淡出，不位移不缩放 | 120ms |

所有时长再乘 `TaskCenterAnimationPolicy.durationMs()` 的档位倍率（见 4.9）。

### 4.7 `LockedAppStore` 的数据形态

内部持有 `volatile Set<String> locked`（当前用户下的已锁包名）。

系统侧的权威格式（`Settings.System` 的 `locked_apps` 键，String）：

```json
[
  {"u": 0,    "pkgs": ["com.example.a", "com.example.b"]},
  {"u": -100, "pkgs": ["com.example.default"]}
]
```

- `u` = userId，`0` 为当前用户
- `u = -100`（`LockedAppStore.DEFAULT_USER_ID`）是**系统预置默认锁定项**，
  `load()` 按传入 `userId` 过滤，默认**不**把预置项算作"用户锁定"
- `rewrite()` 只重写自己那一组，其余分组原样保留 —— 整串覆盖会抹掉 `u=-100` 的预置项

## 5. 接口清单

以下按用户要求的四类主线 + 三类配套组织。每个接口给出：**职责 / 调用方式 / 入参 / 出参 / 降级 / 调用者**。

---

### 5.1 任务应用接口（Task）

#### 5.1.1 `RecentTaskRepository.loadRunningTasks(int maximum, boolean includeSnapshots)`

| 项 | 内容 |
|---|---|
| **职责** | 读取当前运行中的任务，转成 `List<RecentTaskPreview>` |
| **调用方式** | `new RecentTaskRepository(context).loadRunningTasks(max, snapshots)`；**必须**在非主线程调（Binder + 快照读取会阻塞） |
| **入参** | `maximum`：期望条数，内部钳制为 `max(2, min(10, maximum))`；`includeSnapshots`：是否取任务快照 |
| **出参** | `List<RecentTaskPreview>`，可能为空，**不返回 null** |
| **原生调用** | `ActivityManager.getRecentTasks(30, RECENT_IGNORE_UNAVAILABLE)` |
| **过滤规则** | ① `taskId < 0` 跳过；② `!isRunning` 跳过；③ `numActivities <= 0` 跳过；④ 包名等于 `HOST_PACKAGE`（模块自身）跳过；⑤ 等于 `SYSTEM_UI_PACKAGE` 跳过；⑥ 等于 `com.miui.home` 跳过 |
| **容错** | 单条任务的 `getApplicationInfo` 失败**只跳过该条**，不中断整体（`catch (Throwable itemError)`） |
| **降级** | `activityManager == null` → 返回空列表；外层异常 → 记日志返回已收集的部分 |
| **调用者** | `FanRuntime.activateSideTasks`（经 `configHandler` 异步） |

> **注意**：过滤用的是**写死的包名常量**而非 `context.getPackageName()`。原因：本类在 SystemUI 进程被调用时，
> 后者返回 `com.android.systemui`，会让"模块自身任务"漏进列表。

#### 5.1.2 `RecentTaskRepository.foregroundTaskId()`

| 项 | 内容 |
|---|---|
| **职责** | 取「按最近使用排序」的第一条任务 id，**用于分屏时快照另一个 stage 的填充对象** |
| **调用方式** | 必须在**唤起列表的瞬间**调用，不能等到启动分屏的那一刻 |
| **出参** | `int`，读不到返回 `-1` |
| **原生调用** | `getRecentTasks(5, RECENT_IGNORE_UNAVAILABLE)` 取首个满足 `isRunning && numActivities>0` 的 |
| **调用者** | `FanRuntime.activateSideTasks` → 存入 `foregroundTaskIdAtListOpen` |

> ⚠️ **此接口的返回值不等于"当前前台"**。刚退到后台的任务也在 `getRecentTasks` 里，
> 且列表呼出瞬间系统会调整任务栈，序列会在数秒内漂移。**不要用它做前台变化判定** —— 见下一个接口。

#### 5.1.3 `RecentTaskRepository.currentForegroundTaskId()`

| 项 | 内容 |
|---|---|
| **职责** | 取系统认定的**当前前台**任务 id，用于前台变化看护 |
| **出参** | `int`，读不到返回 `-1`（调用方应按"未知"处理，**不触发关闭**） |
| **原生调用** | `ActivityManager.getRunningTasks(1)` 取头部 |
| **为何不用 `getRecentTasks`** | 实测：用 `getRecentTasks` 做基准会造成误判，表现为**列表无故自动关闭** |
| **调用者** | `FanRuntime.startForegroundWatch`（取基准）、`runForegroundWatch`（轮询比对） |

#### 5.1.4 `RecentTaskRepository.launch(RecentTaskPreview task)`

| 项 | 内容 |
|---|---|
| **职责** | 把某个任务带回前台（**全屏**） |
| **调用方式** | `repository.launch(task)` |
| **入参** | `RecentTaskPreview`（只用 `taskId`） |
| **出参** | `boolean`（是否至少一条路径成功） |
| **降级链（三级）** | ① `startActivityFromRecents(taskId, centeredScaleOptions)`（带居中缩放的系统动画）<br>② `startActivityFromRecents(taskId, ActivityOptions.makeBasic())`（无动画）<br>③ `ActivityManager.moveTaskToFront(taskId, MOVE_TASK_WITH_HOME)` |
| **原生调用细节** | 反射 `android.app.ActivityTaskManager.getService()` → `startActivityFromRecents(int, Bundle)`；结果 `< 0` 视为失败 |
| **调用者** | `FanRuntime.showLoadedSideTasks` 的 `onLaunch` 回调 |

> **失败判据**：`startResultFailed(result)` = `result instanceof Number && intValue() < 0`。
> 之所以要判，是因为该反射调用**不抛异常也可能返回失败码**。

#### 5.1.5 `RecentTaskRepository.removeTask(int taskId)` / `removeAllTasks(List)`

| 项 | 内容 |

#### 5.2.2 `HyperOsFreeformBridge.launchIntentNow(...)`（核心实现，private）

```java
private boolean launchIntentNow(String packageName, Intent intent, GestureConfig config,
                                Runnable onLaunchArmed, boolean shortcutLaunch,
                                RuntimeTarget shortcutTarget)
```

**这是整个小窗能力的落点。** 关键步骤：

```
1. Class<?> manager = XposedHelpers.findClass("miui.app.MiuiFreeFormManager", classLoader)
2. Object result = XposedHelpers.callStaticMethod(manager, "getActivityOptions",
                                                    context, packageName, true, false)
3. options = (result instanceof ActivityOptions) ? result
           : { ActivityOptions.makeBasic(); setLaunchWindowingMode(5); }   ← 降级
4. scale = readFreeformScale(options)
   nativeBounds = readNativeLaunchBounds(options)
   nativeLandscapeLaunch = FreeformOrientationPolicy
                             .shouldUseNativeLandscapeLaunch(isRotationLockedToPortrait(),
                                                             requestedOrientation(intent))
5. 若 config.customWindowBoundsEnabledFor(是否横屏) && !nativeLandscapeLaunch
     → launchBounds = customLaunchBounds(config, scale, nativeBounds)
     → options.setLaunchBounds(launchBounds)
6. 若 shortcutLaunch → options.setForceLaunchNewTask()
7. existing = findRunningTask(packageName, userId)
   若存在 → forceTaskResizable(existing.taskId)
8. beginPendingMatch(...)   ← 登记"预期出现的那个小窗"，供后续动画/边界校正匹配
   notifyLaunchArmed(onLaunchArmed)
9. 分三路启动：
   - shortcutLaunch            → dispatchShortcut(target, launchOptions)
   - userId != 0              → 广播请求 com.miui.home 以指定 user 启动
   - 否则（常规）              → context.startActivity(intent, launchOptions)
10. scheduleScans()   ← 排定时扫描，匹配预期小窗
```

| 项 | 内容 |
|---|---|
| **窗口模式常量** | `setLaunchWindowingMode(5)` = `WINDOWING_MODE_FREEFORM` |
| **降级** | `MiuiFreeFormManager` 不可用 / `getActivityOptions` 抛错 → 用 `ActivityOptions.makeBasic()` + 窗口模式 5 |
| **失败处理** | 整体 `catch (Throwable)` → `clearPendingMatch()` + 记日志 + 返回 `false`（**不残留 pending 状态**，否则后续匹配会错乱） |
| **副作用** | 会写 `pendingMatch` 系列字段，必须由 `onTaskAppeared` / `onTaskInfo` / `abandonStalePendingLaunch` 三者之一收尾 |

### 5.3 锁定应用程序接口（Lock）

#### 5.3.1 `LockedAppStore`（读 + 缓存 + 订阅）

| 方法 | 签名 | 职责 | 入参 | 出参 |
|---|---|---|---|---|
| 构造 | `LockedAppStore(Context, int userId)` | 绑定 context 与用户 | `userId` 来自 `currentUserId()` | — |
| 取用户 | `static int currentUserId()` | 反射 `UserHandle.myUserId()` | — | `int`，失败兜底 `0` |
| 读 | `Set<String> load()` | 直读 `Settings.System("locked_apps")` 并解析 | — | 当前用户锁定包名集合，**失败返回空集合而非 null** |
| 快照 | `Set<String> snapshot()` | 取上次 `load()` 结果（供 `onDraw` 每帧读取，不重复解析） | — | `Set<String>` |
| 查询 | `boolean isLocked(String pkg)` | 单包判定 | 包名 | `boolean` |
| 刷新 | `boolean refresh()` | 重读并与缓存比对 | — | **是否发生变化**（变了才需要重绘） |
| 写 | `boolean setLocked(String pkg, boolean shouldLock)` | 见 5.3.3 | 包名、目标状态 | 是否至少一条路径成功 |
| 订阅 | `void startObserving(Runnable onChanged)` | 注册 `ContentObserver` 监听该键 | 变化回调 | — |
| 退订 | `void stopObserving()` | 注销 | — | — |
| 释放 | `void release()` | 置 `released`、退订、清集合 | — | — |

**订阅语义**：`ContentObserver.onChange` 内先 `refresh()`，**仅当返回值 true 才回调** `onChanged.run()`。
这样避免"写自己触发自己重绘"的死循环。

#### 5.3.2 `LockedAppBridge.setLocked(String, int, boolean)`（写，原生）

| 项 | 内容 |
|---|---|
| **职责** | 调 MIUI 自己的应用锁定写入口 |
| **调用方式** | `LockedAppBridge.setLocked(pkg, userId, locked)`（全静态） |
| **原生签名** | `miui.process.ProcessManager.updateApplicationLockedState(String packageName, int userId, boolean locked)`<br>（`public static`，参数类型 `String, int, boolean`） |
| **出参** | `true` = 已通过原生接口送达；`false` = 原生接口不可用，**调用方应回退** |
| **方法解析** | `resolve()` 三重检查（`updateUnavailable` 终态 → `updateMethod` 缓存 → 同步块内重新解析），解析成功后 `setAccessible(true)` 并缓存 |
| **失败终态** | 类/方法不存在 → 置 `updateUnavailable = true`，**不再重试**（避免每次调用抛异常） |
| **调用失败** | 不再尝试别的签名（签名唯一），直接返回 `false` 交调用方降级 |
| **可用性探测** | `static boolean isAvailable()` |

#### 5.3.3 `LockedAppStore.setLocked(...)`（写的完整策略）

```
1. 入参校验（null / 空 → false）
2. 计算 current = locked ∪ {pkg} 或 locked \ {pkg}
   changed == false → return true（幂等短路）
3. 首选：native_ok = LockedAppBridge.setLocked(pkg, userId, shouldLock)
4. 若 !native_ok → 降级：raw = rewrite(current)
                     ok = Settings.System.putString(resolver, "locked_apps", raw)
5. ok → locked = current（本地快照立即跟进，保证连点不被 !changed 短路）
6. 日志区分 via=ProcessManager / via=Settings
```

**为什么必须优先走 `ProcessManager`（实测教训）**：
直接写 `Settings` 虽然改了"权威源头"，但它是**数据旁路** —— 绕过 `ProcessManagerService`
的业务处理。后果：system_server 内存态会更新（`service call ProcessManager 12` 能查到），
但 **launcher 侧的 `Task.isLocked` 缓存收不到通知刷新**，表现为"模块里锁上了、原生任务中心看不到"。

**为什么不 hook launcher 的 `Task.isLocked`**：强耦合桌面版本，升级即碎。

#### 5.3.4 锁定状态的原生链路（重构必读）

```
Settings.System("locked_apps")                              ← LockedAppStore 直读这层
  ↑ saveLockedAppIntoSettings / loadLockedAppFromSettings
ProcessPolicy.sLockedApplicationList (HashMap)              ← system_server 内存态
  ↑
ProcessManagerService.getLockedApplication(int)             ← miui-services.jar
  ↑ IProcessManager（Binder，服务名 "ProcessManager"）
miui.process.ProcessManager.isLockedApplication(String,int)  ← 读
miui.process.ProcessManager.updateApplicationLockedState(...) ← 写 ← LockedAppBridge 反射这层
  ↑
Task.isLocked / TaskView.onLockedChanged                    ← launcher 缓存副本（UI 读这层）
```

**锁定作用机制**：`ProcessPolicy.promoteLockedApp` 提升目标进程 adj 到 `maxAdj + 1`，
解锁后回落 `cch + 101`。所以"清理时保留"靠的是**提 adj 防杀**，不是单纯打标记。

#### 5.3.5 视图层的锁定交互

| 入口 | 触发 | 行为 | 是否关列表 |
|---|---|---|---|
| 行内锁形 | `handleTap` 命中 `lockX ± 20dp` | `onToggleLock(task, !isLocked(pkg))` → `FanRuntime.applyLockChange` | **否** |
| 菜单项 | `ACTION_LOCK` | 同上 | **是**（`EXIT_YIELD`） |

**命中区设计**：`ACTION_HIT_RADIUS_DP = 20f` → 每段 40dp 宽，接近 Apple 最小触摸目标 44dp。
面板仅 280dp，再宽会挤掉应用名。锁区与关闭区**严格按锁区右缘切开**，中间留 4dp 缝。
**无 `lockedApps` 时，锁区整块回退成关闭区** —— 不让点击落空。

#### 5.4.1 `FanRuntime.launchTaskInSplit(int taskId, int foregroundTaskId)`（private）

正常路径下窗口早已撤掉，`view == current` 判断让兜底自然落空。

#### 5.5.3 `TaskCenterListView.configure(...)`

```java

```

| 项 | 行为 |
|---|---|

> **生命周期提示**：`lockedApps` 由 `FanRuntime` 长期持有并注入。列表视图会被反复创建销毁，
> **状态源不能跟着被回收重建**。

#### 5.5.4 `TaskCenterListView` 的布局尺寸与动画常量（供重构对齐）

#### 5.5.5 图标绘制规则（`drawFittedIcon`）

```

先等比缩放到目标尺寸，再裁形
```

### 5.6 跨进程接口（IPC）——**当前已停用**

> **重构者必读**：这一整层是历史产物。当前主链路**完全不经过它**。
> 保留在仓库里是为了可回退，不是可依赖的接口。

#### 5.6.1 停用原因

第三档曾被改为「模块进程的普通 Activity（`ty=1`）承载 + 交系统生命周期关闭」。
实测两个不可接受缺陷：

1. **应用窗口独占** —— 呼出时屏幕切成一个"独立的列表界面"，不是浮层观感；
2. **上划走系统 task 过渡** —— 明显卡顿。

故改回 SystemUI 进程内的 `ty=2038` overlay，数据不再需要跨进程搬运。

#### 5.6.2 存量定义（仅供理解历史 / 若未来恢复时参考）

**动作常量**（`TaskCenterActionContract`）：

| 常量 | 值 | 方向 | 现状 |
|---|---|---|---|
| `ACTION_SHOW` | `...action.TASK_LIST_SHOW` | SystemUI → 模块进程 | **无发送方**（死代码） |
| `ACTION_STARTED` | `...action.TASK_LIST_STARTED` | 模块进程 → SystemUI | 仅废弃 Activity 发；`FanRuntime.onTaskListStarted()` 已改空操作 |
| `ACTION_SPLIT` | `...action.TASK_LIST_SPLIT` | 模块进程 → SystemUI | 仅废弃 Activity 发 |
| `ACTION_FREEFORM` | `...action.TASK_LIST_FREEFORM` | 模块进程 → SystemUI | 仅废弃 Activity 发 |

**EXTRA 键**：`EXTRA_TASK_ID`=`task_id`、`EXTRA_PACKAGE`=`package_name`、`EXTRA_MAX_COUNT`=`max_count`

**包名常量**：`SYSTEM_UI_PACKAGE`=`com.android.systemui`、`SENDER_PACKAGE`=`HOST_PACKAGE`=`com.oxohang.fanfreeform`

**发送手法**（`TaskCenterIpc.sendToPackage`）：
```java
request.setPackage(targetPackage);
Bundle options = BroadcastOptions.makeBasic().setShareIdentityEnabled(true).toBundle(); // API 34+
context.sendBroadcast(request, null, options);
```
必须共享身份，否则接收端 `BroadcastSenderValidator.isFromPackage()` 验不出来源，会把匿名广播当非授权来源丢弃。

**数据搬运**（`TaskCenterIpc.publishTaskList` → `ConfigProvider`）：
```java
// 发布（SystemUI 进程）
resolver.call(ConfigContract.URI, METHOD_REPORT_TASK_LIST, null, extras);
//   extras: EXTRA_TASK_IDS(int[]) / EXTRA_TASK_PACKAGES(ArrayList<String>) / EXTRA_TASK_LABELS(...)
//   Provider 内部打 EXTRA_TASK_LIST_TIME 时间戳

// 取用（模块进程）
resolver.call(ConfigContract.URI, METHOD_GET_TASK_LIST, null, null);
//   超时：TASK_LIST_SNAPSHOT_MAX_AGE_MS = 2000L
//   取后即清（snapshot = null），过期也清 —— 避免显示已经关掉的任务
```
⚠️ `publishTaskList` **当前无任何调用者**（死代码）。

**Activity 注册**（`AndroidManifest.xml`）：
```xml
<activity android:name=".xposed.TaskCenterListActivity"
          android:exported="false"
          android:excludeFromRecents="true"
          android:launchMode="singleInstance"
          android:taskAffinity=""
          android:configChanges="orientation|screenSize|screenLayout|smallestScreenSize|keyboardHidden|uiMode|density"
          android:theme="@android:style/Theme.Translucent.NoTitleBar" />
```

**重构建议**：可直接删除 `TaskCenterIpc` / `TaskCenterActionContract` / `TaskCenterActionReceiver` /
`TaskCenterListActivity` 及 Manifest 条目，并移除 `ConfigProvider` 的
`METHOD_REPORT_TASK_LIST` / `METHOD_GET_TASK_LIST` 分支。删除前确认没有外部调用方。

### 5.7 与其它系统能力的对接接口

#### 5.7.1 手势输入（唤起入口）

| 项 | 内容 |
|---|---|
| **接口** | `InputSource.start(Context, MotionListener)`（`rom/InputSource.java`） |
| **实现** | `Os1GestureMonitorInputSource` → 框架 `monitorGestureInput` 注册 |
| **返回** | `BridgeResult<Void>`；失败如实返回原因，**不做自建兜底窗口** |
| **能力** | 注册后框架直接投递手势事件，并返回 `InputMonitor`，业务层因此具备 `pilferPointers()` 抢占能力（与 OS3 事件控制器同一套机制） |
| **任务中心的使用点** | `FanRuntime.activateSideList` → `sideLayoutMode == SIDE_LAYOUT_TASKS` → `activateSideTasks(x, y)` |

**档位分派（`activateSideList`）**：

```java
int sideLayoutMode = currentSideLayoutMode();
if (sideLayoutMode == SIDE_LAYOUT_SYSTEM_RECENTS) { activateSystemRecents(); return; }
if (sideLayoutMode == SIDE_LAYOUT_TASKS)          { activateSideTasks(x, y); return; }
if (sideLayoutMode == SIDE_LAYOUT_HONEYCOMB)      { activateSideHoneycomb(x, y); return; }
// 其余：扇形 / 环形 / 列表 —— 走通用图标路径
```

`sorLayoutMode` 常量值：`SIDE_LAYOUT_LIST=0`、`RING=1`、`FAN=2`、`HONEYCOMB=3`、**`TASKS=4`**、`SYSTEM_RECENTS=5`。

#### 5.7.2 `FanRuntime.activateSideTasks(float x, float y)`（唤起时序的起点）

```java
foregroundTaskIdAtListOpen = recentTaskRepository.foregroundTaskId();  // ① 先快照
state = State.TASKS_LOADING;
activeSideList = true;
outsideCapture.remove();          // ② 摘掉外部触摸捕获层（避免重叠）
outsideGestures.clearAll();
taskLoadCurrentX = x; taskLoadCurrentY = y;
int generation = ++taskLoadGeneration;                                  // ③ 代次，防过期回调
GestureGeometry.Corner taskCorner = corner;
GestureConfig taskConfig = config;
configHandler.post(() -> {                                              // ④ 后台读
    List<RecentTaskPreview> previews = recentTaskRepository.loadRunningTasks(
            taskConfig.sideTaskMaxCount,
            taskConfig.sideTaskLayoutMode == SIDE_TASK_LAYOUT_FLAT);
    mainHandler.post(() -> showLoadedSideTasks(previews, taskCorner, x, y,
            taskConfig, generation));
});
```

**三个必须保留的设计点**：

| 设计 | 原因 |
|---|---|
| ① 先快照 `foregroundTaskIdAtListOpen` | 分屏要用它填 side stage。**不能在启动分屏时现取** —— 那时前台已是目标任务 |
| ③ `taskLoadGeneration` 代次 | 用户在加载期间抬手 / 再触发，旧回调必须作废。`showLoadedSideTasks` 开头即校验 |
| ④ `sideTaskLayoutMode == FLAT` 作为 `includeSnapshots` | 只有视差卡片档需要快照位图；列表档不画快照，省掉最贵的一次硬件位图读取 |

#### 5.7.3 系统面板（通知栏 / 控制中心）联动

| 项 | 内容 |
|---|---|
| **入口** | `FanRuntime.applySystemPanelCaptureState(String source)` |
| **展开时** | 压力手势取消 → 蜂窝 `removeNow` → `outsideCapture.remove()` → `honeycombOverlay.setPaused(true)` → `outsideGestures.clearAll()` → **`setTaskSurfacePaused(true)`** |
| **收起时** | **`setTaskSurfacePaused(false)`** → `syncPressureDebugOverlay()` → `honeycombOverlay.setPaused(false)` → `refreshOutsideCapture()`（立即 + 90ms + 260ms） |

**语义分层（关键）**：

| 场景 | 处理 | 为什么 |
|---|---|---|
| 下拉通知栏 | **退位不销毁**（缩小变暗） | 用户"看一眼通知"不等于"关掉列表" |
| 真的切走应用 | 由前台看护按 `EXIT_YIELD` 收尾 | 这才是终局 |
| 从面板点了"当前已在前台的那个应用" | 列表**原样弹回** | taskId 未变，前台看护无从判断 —— 刻意选择，用户没有要求它消失 |

#### 5.7.4 前台看护（`startForegroundWatch` / `runForegroundWatch`）

| 项 | 值 |
|---|---|
| 轮询间隔 | `FOREGROUND_WATCH_INTERVAL_MS = 200L` |
| 确认次数 | `FOREGROUND_WATCH_CONFIRM_HITS = 2`（连续两次读到同一新 id 才判定） |
| 基准 | `currentForegroundTaskId()`（`getRunningTasks(1)`） |
| 基准读不到 | **不启动看护**，`foregroundWatchActive = false`，只记日志 |
| 判定为切换 | `EXIT_YIELD` 退场 + 停表 |

**为什么基准读不到就不启动**：宁可漏掉一次"从前台切走"的自动关闭（用户仍可用上划/点外部等
既有通路），也不能让"首次读到有效值"被误判成一次切换而把列表错误收掉。

**为什么需要两次确认**：避免切换瞬间的 id 抖动误触。

#### 5.7.5 底部上划（全局手势回调，**不依赖 state**）

```java
if (taskSwitcherOverlay.isVisible()) {          // ← 判据是"窗口可见"，不是 state
    if (action == ACTION_DOWN) {
        bottomSwipeDownY = y; bottomSwipeDownX = x;
        bottomSwipeArmed = y >= height - BOTTOM_SWIPE_START_ZONE_DP * density;  // 96dp
    } else if (bottomSwipeArmed && action == ACTION_MOVE) {
        float dy = bottomSwipeDownY - y;
        float dx = Math.abs(x - bottomSwipeDownX);
        if (dy > BOTTOM_SWIPE_MIN_DISTANCE_DP * density && dy > dx * 1.5f) {   // 48dp
            dismissTaskSurfaceForForegroundChange("bottom swipe-up", EXIT_QUIET);
        }
    }
}
```

> ⚠️ **这段代码的位置是架构性的**：它必须写在
> `if (honeycombOverlay.isVisible() || taskSwitcherOverlay.isVisible()) return;` **之前**。
> 否则 IDLE 态的触摸会先被那个 return 拦掉，表现为"上划对列表毫无反应"。

#### 5.7.6 系统原生最近任务（另一条独立通路）

|---|---|
| **类** | `SystemRecentsLauncher`（`show()` / `isVisible()`） |

#### 5.7.8 侧边返回手势（跟手让位）

| 项 | 内容 |
|---|---|
| **入口** | `FanRuntime.handleTouchEvent` 内 `taskSwitcherOverlay.isVisible()` 分支（**必须在 `return` 之前**） |
| **进度换算** | `p = clamp01(inward / (TaskCenterListView.BACK_YIELD_TRAVEL_DP × density))`，`inward` = 从左边缘起 `x − downX`、从右边缘起 `downX − x` |
| **只增不减** | `if (p > backYieldProgress)` 才更新 —— 手指回撤时面板不跟着缩回，否则来回抖 |
| **投递** | `taskSwitcherOverlay.setBackYield(p, fromLeft)` → `TaskCenterListView.setBackYieldProgress(...)` |
| **收尾（UP）** | 系统没抢指针 = 返回未触发 → `releaseBackYield()` 弹回原位，列表继续留着 |
| **收尾（CANCEL 且 progress ≥ 0.12）** | 系统抢走了指针 = 返回已触发 → `dismissTaskSurfaceForForegroundChange("back gesture", EXIT_YIELD)` |
| **绝不 pilfer** | 列表窗口是全屏 overlay，底下应用收不到触摸，系统返回手势靠它自己的 `InputMonitor` 旁听 + `pilferPointers()` 执行。**模块若抢，用户的返回就没了** |
| **为何用 CANCEL 判定** | 系统抢走指针时本通道收到 `ACTION_CANCEL`，这是"返回确实触发"的可靠信号，比等前台看护（200ms × 2 次确认）快得多，也让列表退场与系统返回动画同时发生 |

## 6. 全链路时序

### 6.1 呼出

```
用户侧边滑动
   ↓
InputSource 投递 MotionEvent 到 FanRuntime
   ↓
手势状态机判定 → activateSideList(x, y, w, h)
   ↓
sideLayoutMode == SIDE_LAYOUT_TASKS (4) ?
   ├─ 否 → 其它档位
   └─ 是 → activateSideTasks(x, y)
              ├ 快照 foregroundTaskIdAtListOpen
              ├ state = TASKS_LOADING
              ├ outsideCapture.remove()
              └ configHandler.post → loadRunningTasks(max, includeSnapshots)
                                       ↓ （Binder：getRecentTasks + 快照）
                                     mainHandler.post → showLoadedSideTasks()
                                       ↓
                                     TaskSwitcherOverlayController.show()
                                       ├ removeNow()（防叠加）
                                       ├ 选 Surface（列表 / 卡片）
                                       ├ windowManager.addView(ty=2038)
                                       └ playEntry()
                                       ↓
                                     state = TASKS
                                     externalMove(锚点)
                                     vibrateTick()（若 haptic）
                                     startForegroundWatch()
```

### 6.2 点应用（全屏）

```
handleTap → 命中行本体
   ↓
listener.onLaunch(task)
   ↓
控制器：先 listener.onLaunch(task)（动作立刻派发），再 playExit(list, EXIT_YIELD)
   ↓
FanRuntime.onLaunch:
   ├ recentTaskRepository.launch(task)
   │    ├ startActivityFromRecents(taskId, centeredScaleOptions)   ← 首选
   │    ├ startActivityFromRecents(taskId, makeBasic())            ← 次选
   │    └ moveTaskToFront(taskId, MOVE_TASK_WITH_HOME)             ← 兜底
   ├ activeRecentTasks = null
   ├ if (state == TASKS) state = IDLE
   └ postDelayed(refreshOutsideCapture, 500ms)
   ↓
视图播 EXIT_YIELD（220ms × 倍率）→ notifyClosed()
   ↓
控制器 onClosed → removeNow() → removeViewImmediate + releaseResources
   ↓
FanRuntime.onClosed → 清 activeRecentTasks / foregroundTaskIdAtListOpen / state / refreshOutsideCapture
```

### 6.3 小窗

```
handleTap → 菜单项 ACTION_FREEFORM
   ↓
listener.onListAction(ACTION_FREEFORM, task, null)
   ↓
控制器：listener.onListAction(...) 后 playExit(EXIT_YIELD)
   ↓
FanRuntime.handleListAction:
   └ freeformTaskByPackage(task.packageName)
        ├ getLaunchIntentForPackage(pkg) → null ? 记日志返回
        └ freeform.launchExternalIntent(pkg, intent, config, refreshOutsideCapture)
             ├ 若当前有正常态小窗且目标不同包
             │    → miniTask(当前) → 等 mini 态 → 再 launchIntentNow
             └ 否则 launchIntentNow:
                  MiuiFreeFormManager.getActivityOptions(ctx, pkg, true, false)
                  → 必要时 setLaunchBounds
                  → beginPendingMatch(...)
                  → context.startActivity(intent, options)
                  → scheduleScans()
   ↓
小窗出现 → hook onTaskAppeared → dismissTaskSurfaceForForegroundChange("freeform task appeared", EXIT_YIELD)
```

**注意时序竞争**：小窗出现会触发 `onTaskAppeared`，与 `EXIT_YIELD` 的出场动画可能重叠。
设计上由 `dismissTaskSurfaceForForegroundChange` 的 `isAttached()` 判据兜住 ——
窗口已撤则直接返回，不重复处理。

### 6.6 关闭（五条通路，全部收敛到同一方法）

| # | 触发 | 入口 | 出场因果 |
|---|---|---|---|
| 1 | 小窗出现 | `onTaskAppeared` → `dismissTaskSurfaceForForegroundChange("freeform task appeared", ...)` | `EXIT_YIELD` |
| 2 | 前台任务变化（桌面/通知/旁路切走） | `runForegroundWatch`（200ms × 2 次确认） | `EXIT_YIELD` |
| 3 | 底部上划 | `handleTouchEvent` 内 `taskSwitcherOverlay.isVisible()` 分支 | `EXIT_QUIET` |
| 4 | 侧边返回手势 | `releaseBackYield` / 让位退场 | `EXIT_YIELD` |
| 5 | 手势状态复位 | `resetFan` 内 `dismissTaskSurfaceForForegroundChange("gesture reset", ...)` | `EXIT_YIELD` |
| — | 点外部 | `FLAG_WATCH_OUTSIDE_TOUCH` → `ACTION_OUTSIDE` → `popLevel(EXIT_RECEDE)` | `EXIT_RECEDE` |
| — | 返回键 | `onKeyDown` → 分层关闭（先收菜单，再收面板） | `EXIT_RECEDE` |

**统一收敛方法**：

```java
private void dismissTaskSurfaceForForegroundChange(String reason, int exitReason) {
    if (!taskSwitcherOverlay.isAttached()) {   // ← 判据：窗口是否真在屏幕上
        stopForegroundWatch();
        return;
    }
    taskSwitcherOverlay.playExit(exitReason);
    stopForegroundWatch();
    boolean wasTasks = state == State.TASKS;
    resetFan(false);
    Log.i("Task surface dismissed: " + reason + " exit=" + exitReason + ...);
}
```

> ⚠️ **架构硬原则（血的教训）**：判据必须是 `isAttached()`，**绝不能是 `state == TASKS`**。
> 侧边栏拉出列表后手指一抬 → `ACTION_UP` 分支 `resetFan(false)` → `state` 归位 `IDLE`，
> 但列表窗口**刻意保留**（抬手后还要点卡片）。用 `state` 判定会让此后所有关闭信号都被判为
> "无需处理"，列表变成关不掉的僵尸层 —— 这正是历史上「上划/开小窗/下拉都不生效」的根因。

### 7.1 依赖图（谁依赖谁）

```
FanRuntime
  ├─ 依赖 TaskSwitcherOverlayController（组合，长期持有）
  ├─ 依赖 RecentTaskRepository（组合）
  ├─ 依赖 LockedAppStore（组合，长期持有，注入视图）
  ├─ 依赖 HyperOsFreeformBridge（组合，跨模块复用）
  ├─ 依赖 SystemRecentsLauncher（组合）
  └─ 被注入：soScSplitController / soScStageCoordinator（来自 FanFreeformHook）

TaskSwitcherOverlayController
  ├─ 依赖 TaskCenterListView（创建）
  ├─ 依赖 TaskSwitcherOverlayView（创建）
  └─ 依赖 Surface / Listener 抽象（不依赖 FanRuntime 类型）

TaskCenterListView
  ├─ 依赖 RecentTaskPreview（只读数据）
  ├─ 依赖 GestureConfig（只读配置）
  ├─ 依赖 LockedAppStore（只读查询 + 订阅）
  ├─ 依赖 Ui（色彩令牌）
  └─ 依赖 TaskCenterListView.Listener（不依赖 FanRuntime / 不依赖任何系统类）

RecentTaskRepository
  ├─ 依赖 ActivityManager / PackageManager / SearchManager / LauncherApps（公开 API）
  ├─ 依赖 ActivityTaskManager（反射）
  └─ 不依赖任何 Xposed 类（硬约束，见 2.2-B）

LockedAppStore
  ├─ 依赖 Settings / ContentResolver / ContentObserver（公开 API）
  └─ 依赖 LockedAppBridge（写）
```

### 7.2 七条关键解耦决策

| # | 决策 | 换来了什么 | 代价 |
|---|---|---|---|
| 1 | **视图只做界面，不碰系统** | 视图可单测、可在别的容器里复用；换 ROM 不用改绘制代码 | 视图需要 Listener 抽象层 |
| 2 | **Listener 两层同构转发** | 控制器可在转发处插入"何时播让位动画"的策略，视图不必知道 | 多一层方法调用 |
| 3 | **判据用 `isAttached()` 而非 `state`** | 消除僵尸层（历史 bug 根因） | 每次关闭都要查窗口状态（成本极低） |
| 4 | **锁定的读与写分离**（`LockedAppStore` 读 / `LockedAppBridge` 写） | 读可以零反射零 hook；写才是原生接口，降级路径清晰 | 两个类 |
| 5 | **`rom` 层只探测能力，不做业务动作** | 换 ROM 只需改 `RomTargets`；业务代码不接触类名 | 小窗启动等能力散在 Bridge |
| 6 | **任务数据只在 SystemUI 进程读** | 权限正确、无跨进程 Bitmap 传输 | 模块进程无法独立支撑该功能（故 Activity 方案被否） |
| 7 | **关闭时机自己掌握，不交给系统生命周期** | 不走系统 task 过渡（上划卡顿根源）、状态归位可控、观感一致 | 需要维护 5 条关闭通路 + 前台看护轮询 |

### 7.3 反依赖：模块刻意不做的事

| 不做 | 原因 |
|---|---|
| 不 hook launcher 的 `Task.isLocked` | 强耦合桌面版本，升级即碎 |
| 不自己算小窗缩放 | 位置/大小"拉伸→收缩"后尺寸漂移，手感不对（历史教训） |
| 不手动重放本模块 hook 的方法（如 `onTaskVanished`） | 递归触发自身 hook + 与系统互等，**实测卡死** |
| 不自建"锁定"概念的状态存储 | 系统已有权威键 `locked_apps`，自建必然不同步 |
| 不在 overlay 上试图获得"系统当前界面"身份 | 实测：本机所有 overlay（2038/2032）都被标记不可聚焦，系统唯一可聚焦临时全屏界面是系统进程持有的 `ty=2040 NotificationShade` |
| 不给列表加"已勾选形态"之类的额外文字提示 | 交互语义应由控件自身表达（历史设计决策） |

## 10. 重构指南（最小可行路径）

若要从零重建，按此顺序可保证每步都可验证：

1. **建窗口骨架**：`ty=2038` + 六个 flag + 一个纯色 `View`。验证点：手势触发后屏幕出现一块浮层，点外部能收到 `ACTION_OUTSIDE`。
2. **接任务数据**：`RecentTaskRepository.loadRunningTasks(n, false)`，把包名打到日志。验证点：条数与系统最近任务一致，且不含模块自身/SystemUI/桌面。
3. **接视图绘制**：先只画行（图标 + 名称 + 分隔线），不做菜单、不做动画。验证点：能看、能点。
4. **接 `launch`**：三级降级链。验证点：点行能回到该应用。
5. **接关闭通路**：先只做"点外部"和"返回键"（`EXIT_RECEDE`）。验证点：能关掉、不留僵尸层。
6. **补五条主动关闭通路**：从小窗出现 / 前台看护 开始（这两条最容易观察到）。验证点：开小窗时列表消失。
7. **接小窗**：`launchIntentNow` 主体。验证点：目标以小窗出现。
8. **接分屏**：`startTask` 两段调用。验证点：两侧各有应用。
9. **接锁定**：先只读（`LockedAppStore`），再写（`LockedAppBridge`）。验证点：模块里锁上后，原生任务中心也显示锁。
10. **补菜单 / 快捷方式 / 搜索 / 应用信息**。
11. **补动画**：四类出场 + 入场 + 橡皮筋 + 返回跟手。

**每步都必须保持的不变式**：

- 依赖方向单向向下（第 3 章）
- `RecentTaskRepository` 不引用 Xposed 类（2.2-B）
- 关闭判据用 `isAttached()`（6.6）
- `foregroundTaskIdAtListOpen` 在唤起瞬间快照（5.7.2）
- 颜色只引用 `Ui` 令牌（5.5.4）

## 11. 待确认项

以下是我在核对中**无法从代码确证**或**发现代码内部不一致**的地方，逐条标注，不做假设。

### 11.1 分屏：`getSideStagePosition()` 读了但未参与决策

- **现象**：`launchTaskInSplit` 内读出了 `sideStagePosition`（注释说明它是 side stage 的物理位置，0=top/left、1=bottom/right，用户可交换且系统记忆），但该值**只写进日志**，实际 `startTask` 的第二个参数被硬编码为 `mainStagePosition = 0` / `sideStagePositionArg = 1`。
- **影响**：如果系统记忆了"side stage 在左侧"，当前实现仍会按逻辑位置 1 调用，实际左右可能与该值不符。是否有害取决于 `startTask` 的 position 参数语义到底是"逻辑编号"还是"物理位置"。
- **需要确认**：`SoScSplitScreenController.startTask(actionTaskId, position, options)` 的 `position` 参数是逻辑槽位编号还是物理位置。若为物理位置，此处存在真实缺陷。

### 11.2 `FanRuntime.applyLockChange` 的 Javadoc 与实现不一致

- **现象**：该方法注释仍写着「**为什么写 Settings 就是"完整动作"**……写进系统认的那个键，就是让系统按它的规则办事」，并称模块无需通知任何服务。
- **实际实现**：`LockedAppStore.setLocked` 已改为**优先**调 `LockedAppBridge`（`ProcessManager.updateApplicationLockedState`），Settings 只是降级路径。
- **影响**：仅文档误导，运行时行为正确（走原生）。但重构者若照注释实现，会得到"通知链断开"的错误版本。
- **建议**：以 `LockedAppStore.setLocked` 与 `LockedAppBridge` 类注释为准（两者已正确反映实测结论）。

### 11.3 `menuShortcuts` 的生产者未定位

- **现象**：`TaskCenterListView.buildMenu()` 会遍历 `menuShortcuts` 生成 `ACTION_SHORTCUT` 菜单项；`configure()` 里将 `menuShortcuts = Collections.emptyList()`，另有字段 `shortcutsRequestedFor` 与 `configure` 注释提到的 `ShortcutHostRuntime`，但本次核对**未找到把 `menuShortcuts` 填充起来的完整调用链**。
- **影响**：若该链确实缺失，则"应用快捷方式"菜单项永远不出现（且不会报错，属静默降级）。
- **需要确认**：`ShortcutHostRuntime` 与 `menuShortcuts` 之间的填充路径是否存在、是否被某分支条件挡住。

### 11.4 `TaskSwitcherOverlayView`（视差卡片档）的 `onToggleLock` 无入口

- **现象**：`TaskSwitcherOverlayController.createCardSurface` 构造的 `TaskSwitcherOverlayView.Listener` 只实现了 `onLaunch` / `onClosed` 两个方法；`TaskCenterListView.Listener` 的 `onToggleLock`、`onCloseTask`、`onCloseAll`、`onListAction` **在卡片档均无入口**。
- **影响**：视差卡片档不支持锁定、关闭单个、全部关闭、菜单动作。这是**有意还是遗漏**，代码里无明确说明。
- **需要确认**：若产品要求卡片档也支持这些动作，需在 `TaskSwitcherOverlayView` 增加对应手势区与 Listener 方法。

### 11.5 IPC 层四个类的删除安全性

- **现象**：`TaskCenterIpc.publishTaskList` 无调用者；`ACTION_SHOW` 无发送方；`TaskCenterListActivity` 仅被 Manifest 与自身引用；`FanRuntime.onTaskListStarted()` 已改为空操作。
- **影响**：整层为死代码，但 `TaskCenterActionReceiver.install()` 仍在 `FanFreeformHook` 第 723 行被调用（注册了三个 action 的接收器）。
- **需要确认**：是否存在**仓库外**的调用方（例如其它模块、快捷方式、Tasker 脚本）在使用这些广播 action。若确认无，可整层删除。

### 11.6 `TaskCenterListView` 的 `ACTION_SEARCH` 不关闭列表

- **现象**：`handleTap` 中搜索按钮分支直接 `listener.onListAction(ACTION_SEARCH, null, null)`，**没有** `playExit`。而控制器侧对 `onListAction` 的处理是 `listener.onListAction(...)` 后**无条件** `playExit(list, EXIT_YIELD)`。
- **实际行为**：控制器确实会关列表，所以看起来正常；但**视图侧的注释与意图（"搜索不关列表"）没有落实**。
- **需要确认**：搜索后是应该关列表（当前实际行为），还是保留列表。若保留，需在控制器侧按 `action` 分流，而不是无条件 `playExit`。

### 11.7 任务条数上限有两处钳制（非缺陷，但改上限必须同步）

- **现象**：`ConfigContract.SIDE_TASK_MAX_COUNT` 范围是 2–10；`RecentTaskRepository.loadRunningTasks`
  内部再钳制 `max(2, min(10, maximum))`。
- **判定**：两处**当前一致，不是缺陷**。
- **风险**：若未来调整上限，必须同步改两处，否则出现"设置里能调到 12、列表只显示 10"的静默截断。
  记在此处用于防止漏改。

### 11.8 类注释与实现不一致：行距

- **现象**：`TaskCenterListView` 类头注释写「面板 280dp、**行距 46dp**、分隔线只覆盖应用名称列」，
  但 `computeMetrics()` 实际为 `panelWidth = min(dp(280), round(width × 0.78))`、`rowPitch = dp(52)`。
- **影响**：纯文档问题，运行时以代码为准（52dp）。但重构者若照注释写 46dp，单行点击目标会
  低于 44dp（Apple 最小触摸目标），手感偏差。
- **建议**：以 `computeMetrics()` 为准；类注释应更新。

### 11.9 环境前提（非代码问题，但影响可移植性）

| 项 | 实测值 | 说明 |
|---|---|---|
| 设备 / ROM | Mi 10S（thyme），HyperOS OS1.0，`V816.0.13.0.UMNCNXM`，Android 14 / API 34 | 所有原生签名均在此环境实测 |
| SystemUI 权限 | 持有 `GET_TASKS` / `MANAGE_ACTIVITY_TASKS` / `WRITE_SETTINGS` | 模块进程无这些权限 |
| 冲突变量 | 设备装有 Thanox（另一 hook AMS 的模块） | 排查异常时须列为变量 |
| 日志位置 | `/data/adb/lspd/log/verbose_*.log` | **logcat 里没有模块日志**；LSPosed 单条上限约 3000 字符 |
